# BloomHer implementation and test report

## Implemented in this revision

1. Removed a duplicate ASHA mothers route definition.
2. Removed automatic insertion of an orphan demo mother every time the API process starts. Demo data is now created explicitly with `python seed.py`.
3. Normalised seeded account roles to the lowercase role values expected by login and API queries.
4. Linked the seeded mother login to its mother profile and added a demo healthcare professional account.
5. Replaced the locally hard-coded, generic screening prompts in the frontend with the canonical EPDS/PHQ-9 question payloads returned by the backend.
6. Centralised the frontend API base URL in `src/lib/api.ts` and made it configurable through `VITE_API_BASE_URL`.
7. Added a non-clinical AI resource-topic classifier (TF-IDF + Logistic Regression) with a confidence fallback and an explicit non-diagnostic disclaimer.
8. Added a synthetic hold-out evaluation script for the topic classifier.
9. Updated project setup, demo-account, design-thinking, fieldwork, and limitation documentation.
10. Replaced the passlib dependency with salted PBKDF2-HMAC-SHA256 password hashing using Python's standard library.

## Checks run in the preparation environment

- Python syntax compilation (`python -m py_compile *.py`): passed.
- Backend FastAPI smoke tests: passed for health, EPDS/PHQ-9 question retrieval, all three demo-role logins, ASHA mother listing, screening submission, safety-item flagging, duplicate-answer rejection, demo referral creation, and AI resource-topic prediction.
- Frontend TypeScript project check (`tsc -b`): passed.
- Frontend ESLint on `src`: passed.
- AI model hold-out test on synthetic phrases: 75 synthetic phrases, 56 train rows, 19 hold-out rows; accuracy 0.79 on this small synthetic split. This is only a software sanity check and is not real-user or clinical validation.

## Build limitation

A complete Vite production bundle could not be confirmed in this preparation environment because the uploaded `node_modules` tree did not contain the platform-specific Rolldown native optional binding. The project archive excludes `node_modules`; run `npm install` from `frontend/` on the target machine, then `npm run build`. TypeScript and ESLint checks did pass here.

## Critical limitations that remain

- API endpoints that use numeric IDs do not yet enforce bearer-token authentication or role/ownership checks. This is a major access-control weakness. The API must remain bound to localhost and use fictional demo data only.
- No production privacy/security controls (HTTPS deployment, encryption at rest, audit logs, rate limiting, session revocation, consent/retention workflows) have been implemented.
- Some ASHA/professional dashboards and follow-up interactions still use local mock data.
- The screening instruments and thresholds require review by the course supervisor/qualified clinical advisor before any real-world use.
- The AI model is trained on synthetic non-clinical phrases only. Its output is a resource-topic suggestion, not a mental-health score, diagnosis, risk assessment, or emergency response.
- Required stakeholder interviews, survey responses, prototype tests, and any associated statistical results must be collected and reported by the student team. They are not generated by this code revision.
